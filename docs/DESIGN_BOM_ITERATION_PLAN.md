# 2D 设计、算料与报价迭代规划

本文档汇总门窗 2D 绘图工具在实际设计、型材算料、报价、下料单场景中的主要问题，并整理后续迭代步骤。

## 一、背景与目标

当前 2D 设计区已经具备基础绘图能力，可以绘制矩形、梯形、尖拱、拱形、平开扇、直线、文字，并支持吸附、成组、标注、撤销重做、3D 预览和导出。

但从门窗设计师的实际工作流看，当前工具仍偏向“通用图形画板”，没有完全变成“门窗构件设计器”。后期如果要支持 120、110、75 等不同型材系列，以及平开、推拉、悬窗、观景窗、异形窗等不同窗型，就必须在设计阶段让每个画布对象带有业务语义，并让算料、报价、下料单直接基于真实设计模型计算。

最终目标：

```text
输入洞口尺寸
选择系列、颜色、玻璃、五金
选择窗型模板或手动绘制外框
添加中梃、分格、固定玻璃、开启扇
实时校验工艺规则
实时生成型材清单、玻璃清单、五金清单、辅料清单
实时生成报价
导出客户图纸、报价单、生产下料单
```

核心原则：

- 画布负责表达窗子结构。
- 系列配置负责决定使用什么型材、五金、玻璃和工艺参数。
- 算料规则负责把结构转成材料清单和下料单。
- 报价规则负责把材料、面积、人工、损耗、利润转成价格。

## 二、当前主要问题

### 1. 2D 图形和 BOM 数据源分离

当前 BOM 计算主要基于 `WindowDesign.panels`，而 2D 画布保存的是 `SketchShape[]`。这会导致画布上看到的真实窗型和 BOM/报价使用的数据可能不一致。

风险：

- 设计图已经修改，但材料清单仍按旧窗型计算。
- 画布中的中梃、异形、平开扇无法完整参与报价。
- CRM 保存的 `designData` 可以还原图形，但不一定能还原可生产、可报价的业务结构。

### 2. 工具语义偏通用图形，不符合门窗设计习惯

当前工具包括“矩形、梯形、尖拱、拱形、直线、文字”等通用绘图概念。门窗设计师更关心的是外框、中梃、固定玻璃、平开扇、推拉扇、上悬扇、纱窗、尺寸标注等业务对象。

问题表现：

- “矩形”到底是洞口、外框、固定玻璃，还是辅助图形不够明确。
- 平开扇依赖在矩形内拖拽生成，开启方向和构件含义不够清晰。
- 工具越多，图形和业务对象之间的映射越难维护。

### 3. 不同系列和窗型会导致算料逻辑差异巨大

同样的外形尺寸，不同系列、不同窗型使用的型材完全不同。

示例：

- 75 平开系列：外框、中梃、平开扇料、压线、合页、执手、传动器、锁点。
- 120 推拉系列：上滑、下滑、边封、勾企、光企、推拉扇料、滑轮、月牙锁。
- 观景窗：大玻璃、加强中梃、拼接件、吊装、运输和安装规则可能单独计价。

如果把这些规则硬编码在绘图工具或单个 BOM 函数里，后期新增系列和窗型会非常困难。

### 4. 缺少设计阶段的工艺校验

自动算料和报价要求设计数据必须可靠。当前设计阶段需要补充以下校验：

- 外框是否闭合。
- 中梃是否连接到外框或其他中梃。
- 格子是否形成封闭区域。
- 开启扇是否有明确归属格。
- 构件是否重叠或悬空。
- 平开扇、推拉扇、玻璃尺寸是否超出系列限制。
- 五金配置是否和开启方式兼容。
- 当前窗型是否允许切换到目标系列。
- 材料库是否缺少对应型材、五金、玻璃或辅料。

### 5. 报价和下料单没有充分区分

报价清单和生产下料单面向不同对象。

报价清单关注：

- 面积。
- 材料汇总。
- 五金、玻璃、辅料。
- 人工、安装、运输、利润、折扣。
- 客户可理解的项目金额。

下料单关注：

- 每根型材的名称、编码、颜色、长度、数量。
- 切角方式。
- 所属位置。
- 损耗率。
- 支料优化和余料管理。

后续应将 `BOM`、`Quote`、`CuttingList` 作为不同输出结果处理。

## 三、建议架构

建议形成以下分层：

```text
DesignModel
  真实门窗结构：外框、分格、中梃、扇、玻璃、开启方式、尺寸

SeriesCatalog
  120、110、75 等系列配置：型材、五金、玻璃、价格、损耗、工艺限制

TemplateCatalog
  平开、推拉、悬窗、观景窗、异形窗等窗型模板

RuleEngine
  校验规则：尺寸范围、系列兼容、五金限制、玻璃限制、结构合法性

BomEngine
  算料：型材清单、玻璃清单、五金清单、辅料清单

CuttingEngine
  下料：逐根型材、长度、数量、切角、位置、损耗、排料

QuoteEngine
  报价：面积价、材料价、人工、安装、运输、利润、优惠
```

## 四、核心数据模型建议

### 1. 设计模型

画布对象不应只是图形，而应是可计算的门窗构件。

```ts
type ComponentKind =
  | 'outerFrame'
  | 'mullion'
  | 'fixedGlass'
  | 'casementSash'
  | 'slidingSash'
  | 'topHungSash'
  | 'screen'
  | 'dimension'
  | 'note';

interface DesignComponent {
  id: string;
  kind: ComponentKind;
  x: number;
  y: number;
  w: number;
  h: number;
  seriesId: string;
  materialRole?: string;
  openingType?: string;
  glassId?: string;
  hardwareSetId?: string;
  parentId?: string;
}
```

建议将 `SketchShape` 逐步升级为 `DesignComponent` 或新增转换层，避免画布数据和报价数据长期分离。

### 2. 系列配置

系列配置负责描述不同型材系列的材料、公式、价格和限制。

```ts
interface ProductSeries {
  id: string;
  name: string;
  category: 'casement' | 'sliding' | 'topHung' | 'view' | 'floating';
  profiles: ProfileRule[];
  hardwareRules: HardwareRule[];
  glassRules: GlassRule[];
  quoteRules: QuoteRule[];
  constraints: ConstraintRule[];
}
```

型材角色应细化，不建议只用 `frame`、`sash`、`mullion` 这类粗粒度名称。

```ts
interface ProfileRule {
  role:
    | 'outerFrameTop'
    | 'outerFrameBottom'
    | 'outerFrameLeft'
    | 'outerFrameRight'
    | 'mullionVertical'
    | 'mullionHorizontal'
    | 'sashTop'
    | 'sashBottom'
    | 'sashLeft'
    | 'sashRight'
    | 'slidingTrackTop'
    | 'slidingTrackBottom'
    | 'hookStile'
    | 'lockStile'
    | 'bead';
  materialId: string;
  lengthFormula: string;
  countFormula: string;
  cutAngle?: string;
  lossRate?: number;
}
```

### 3. 窗型模板

窗型模板负责描述结构，而系列负责描述用料。两者不要混在一起。

```ts
interface WindowTemplate {
  id: string;
  name: string;
  type: 'fixed' | 'casement' | 'sliding' | 'topHung' | 'view' | 'custom';
  allowedSeriesIds: string[];
  defaultComponents: DesignComponent[];
}
```

示例：

- 一固定一平开：外框 + 竖中梃 + 固定玻璃 + 平开扇。
- 两轨两扇推拉：外框 + 上滑 + 下滑 + 两扇推拉 + 两块玻璃 + 滑轮 + 锁。
- 观景窗：外框 + 大玻璃 + 加强中梃或拼接件。

## 五、算料与报价规则

### 1. BOM 和下料单分离

建议输出两类清单：

```ts
interface MaterialBomItem {
  category: 'profile' | 'glass' | 'hardware' | 'accessory' | 'labor' | 'install';
  materialId: string;
  name: string;
  spec: string;
  unit: string;
  quantity: number;
  unitPrice: number;
  amount: number;
}

interface CuttingItem {
  materialId: string;
  code: string;
  name: string;
  color: string;
  lengthMm: number;
  quantity: number;
  cutAngleLeft?: string;
  cutAngleRight?: string;
  position: string;
  sourceComponentId: string;
}
```

### 2. 使用策略模式组织窗型算法

不要使用大量 `if series === '120' && type === 'sliding'` 的硬编码。建议按窗型建立计算器：

```ts
interface BomCalculator {
  supports(series: ProductSeries, design: DesignModel): boolean;
  compute(input: BomInput): BomResult;
}
```

计算器示例：

- `CasementBomCalculator`：平开窗算料。
- `SlidingBomCalculator`：推拉窗算料。
- `TopHungBomCalculator`：悬窗算料。
- `ViewWindowBomCalculator`：观景窗算料。
- `CustomShapeBomCalculator`：异形窗算料。

### 3. 报价规则独立配置

报价不要等同于材料成本。建议支持：

- 按平方报价。
- 按材料成本加损耗、人工、利润报价。
- 单樘最低面积。
- 开启扇加价。
- 异形窗加价。
- 颜色加价。
- 玻璃规格加价。
- 五金品牌加价。
- 安装、运输、楼层、包装加价。
- 折扣和抹零。

```ts
interface QuoteRule {
  id: string;
  name: string;
  applyTo: 'area' | 'profile' | 'glass' | 'hardware' | 'labor' | 'install' | 'specialShape';
  formula: string;
  minCharge?: number;
}
```

## 六、2D 设计区交互改造建议

### 1. 工具栏改为门窗构件工具

建议从当前通用图形工具逐步调整为：

- 结构：外框、竖中梃、横中梃、分格。
- 构件：固定玻璃、平开扇、推拉扇、上悬扇、纱窗。
- 标注：尺寸、文字、辅助线。
- 操作：选择、移动、删除、撤销、重做。

### 2. 采用“先结构，后构件”的设计方式

推荐工作流：

```text
画外框
用中梃/分格形成封闭格子
选择格子
指定固定玻璃、平开扇、推拉扇等构件
右侧编辑系列、玻璃、五金、开启方向
实时生成清单和报价
```

### 3. 系列切换必须做兼容性检查

切换系列时不能只替换 `seriesId`。系统需要判断：

- 当前窗型是否允许使用目标系列。
- 当前开启扇能否转换。
- 原五金是否仍然有效。
- 型材角色是否都有对应材料。
- 哪些尺寸会因框宽、搭接量、玻璃槽变化而重新计算。

若存在风险，应提示用户确认或给出转换建议。

### 4. 实时材料影响提示

选中构件后，右侧面板应显示该构件带来的材料影响。

示例：

```text
平开扇 F1
扇料：横料 680mm × 2，竖料 1180mm × 2
压线：610mm × 2，1110mm × 2
玻璃：596 × 1096 × 1
五金：合页 × 2，执手 × 1，传动器 × 3，锁点 × 6
```

## 七、迭代步骤

### 第 0 阶段：梳理规则和样本数据

目标：先把真实业务样本沉淀下来，避免技术实现脱离实际生产。

任务：

- 收集 75、110、120 至少三个系列的型材清单、单价、损耗、切角规则。
- 收集平开、推拉、悬窗、观景窗的典型样例。
- 收集真实报价单和下料单格式。
- 明确客户报价图和生产加工图需要展示的字段。

产出：

- 系列配置样本。
- 窗型模板样本。
- BOM 样本。
- 下料单样本。
- 报价规则样本。

### 第 1 阶段：统一设计数据源

目标：让画布数据成为 BOM 和报价的可靠来源。

任务：

- 给当前 `SketchShape` 增加业务字段，如 `kind`、`materialRole`、`openingType`、`seriesId`、`glassId`、`hardwareSetId`。
- 新增 `DesignModel` 类型，逐步替代或包裹 `SketchShape`。
- 实现 `buildDesignModelFromShapes()`，把现有画布图形转换为可计算结构。
- 调整保存逻辑，确保 CRM `designData` 保存的不只是图形，还包含业务属性。

验收标准：

- 画布上新增或修改构件后，设计模型同步变化。
- 保存再打开方案后，图形和业务属性都能恢复。

### 第 2 阶段：构件化工具栏

目标：把通用图形工具升级为门窗构件工具。

任务：

- 将“矩形”拆分或改名为“外框”“固定玻璃”。
- 新增“竖中梃”“横中梃”工具。
- 平开扇工具增加明确的左开、右开、内开、外开、上悬等属性。
- 修复快捷键冲突，例如梯形和文字不能同时使用 `T`。
- 增加连续绘制模式，避免每绘制一次都强制切回选择。

验收标准：

- 设计师可以按门窗构件而不是基础图形完成常见窗型。
- 每个构件都有明确业务类型。

### 第 3 阶段：基础 BOM 从画布生成

目标：画完基础窗型即可生成材料清单。

任务：

- 新增 `computeBomFromDesignModel()` 或 `computeBomFromShapes()`。
- 先支持矩形外框、固定玻璃、平开扇、竖中梃、横中梃。
- `BomTable`、`QuotePanel` 优先使用画布设计模型计算；画布为空时再回退到旧 `WindowDesign.panels`。
- 增加构件级材料预览。

验收标准：

- 绘制一固定一平开后，能自动生成外框、中梃、扇料、压线、玻璃、五金清单。
- 修改尺寸后，清单实时更新。

### 第 4 阶段：系列配置化

目标：支持不同系列使用不同型材、五金和计算参数。

任务：

- 建立 `SeriesCatalog` 配置结构。
- 为 75 平开、110 平开、120 推拉建立样本配置。
- 型材角色细化为外框上横、外框下横、边框、中梃、扇横、扇竖、上滑、下滑、勾企、光企、压线等。
- 将当前 BOM 中硬编码的 `frame`、`sash`、`mullion`、`bead` 逐步迁移到配置规则。

验收标准：

- 同一窗型切换不同系列后，材料名称、数量、长度、价格按系列变化。
- 缺少材料配置时有明确错误提示。

### 第 5 阶段：窗型模板化

目标：快速生成常见窗型，并限制系列兼容性。

任务：

- 建立 `WindowTemplate` 配置。
- 支持固定窗、一固定一平开、两固定一平开、两轨两扇推拉、三轨推拉、上悬窗、观景窗等模板。
- 模板声明允许使用的系列。
- 模板生成默认构件，用户再微调尺寸和分格。

验收标准：

- 选择模板和系列后能自动生成初始窗型。
- 不兼容的系列和窗型不能静默套用。

### 第 6 阶段：工艺规则校验

目标：设计时发现不能生产、不能报价或材料缺失的问题。

任务：

- 新增 `validateDesign()`。
- 校验外框闭合、中梃连接、格子封闭、构件归属、尺寸范围、系列兼容、五金兼容、玻璃限制。
- 在画布和右侧属性面板显示问题。
- 严重错误阻止导出生产下料单，普通警告允许用户确认后继续。

验收标准：

- 结构错误和材料缺失不会生成错误清单。
- 用户能清楚知道问题位置和修改建议。

当前进度：目标 6 已完成 —— `validateDesignModel()` 已覆盖结构校验（外框/面板/孤立引用/归属树）、构件级归属（越界、父容器逃逸、中梃连接）、格子封闭几何检测（中梃分割线网格 + 连通分量分析：跨线 `GRID_VIOLATION`、同格无分隔 `UNSEGMENTED`、空分格 `CELL_UNCOVERED`，推拉轨道区域豁免）、同级重叠检测、尺寸与玻璃限制（系列 `constraints` 可配置，未配置回退默认值）、系列-窗型族冲突、五金限制（开启方式/铰链侧）、模板系列兼容（修正了 `allowedFamilies` 恒兼容缺陷）、材料完整性（玻璃缺失、型材角色缺失）；右侧面板按错误/警告/提示分组展示并可点击定位画布构件，生产下料单导出前存在 error 级问题时被拦截。

### 第 7 阶段：报价引擎独立化

目标：支持不同报价方式和业务策略。

任务：

- 新增 `QuoteEngine`。
- 支持面积价、材料成本价、开启扇加价、异形加价、颜色加价、玻璃加价、五金加价、安装运输包装、最低面积、折扣。
- 报价规则配置化。
- 报价单和 BOM 解耦，允许同一 BOM 使用不同报价策略。

验收标准：

- 同一设计可以按不同报价策略计算。
- 报价明细能解释每一项金额来源。

当前进度：目标 7 已完成 —— `quoteFromBom()`（QuoteEngine）已支持面积单价模式（`areaPricePerM2`，按洞口面积计价、与 BOM 解耦）与材料成本加成模式（材料/辅料/加工/安装/损耗 + 开启扇加价、异形加价、颜色加价表、五金档位加价表、玻璃加价、包装费、运输费，全部随樘数与折扣统一放大）；`QuoteRuleSet` 配置化、同一 BOM 可切换策略；报价明细每行含名称/来源 detail；`QuotePanel` 增加「材料成本加成 / 面积单价」策略切换并展示计价方式说明，画布异形/开启扇/颜色/五金档位自动传入引擎。

### 第 8 阶段：下料单与排料优化

目标：支持生产加工。

任务：

- 新增 `CuttingEngine`。
- 输出逐根型材清单，包含长度、数量、颜色、位置、切角、损耗。
- 支持 6 米料或指定原材料长度排料。
- 支持余料统计。
- 区分客户报价图和生产加工图。

验收标准：

- 可导出生产下料单。
- 下料单能追溯到画布构件。

当前进度：目标 8 已完成 —— `computeCuttingList()` 输出逐根型材（编码/名称/颜色/长度/数量/切角/位置/构件来源，长度含损耗），切角按角色细化（中梃两端 90° 直切，外框/扇料按系列 45°/90° 组角）；`optimizeCuttingPacks()` 按型材+颜色分组做 best-fit 排料；新增余料管理：`CuttingResult.remnants` 汇总每支原料余料并按 `minReuseLengthMm`（默认 300）标记可再利用，输出总余料/可再利用余料统计；前端下料面板新增「逐根下料明细」表与可再利用余料标签，支持逐根明细 CSV 与排料 CSV、下料 PDF（含余料区块）；core 测试 62 项全绿。

### 第 9 阶段：复杂窗型扩展

目标：扩展悬窗、观景窗、异形窗、组合窗等复杂场景。

任务：

- 增加更多窗型计算器。
- 完善异形玻璃、异形框料、加强件、拼接件规则。
- 支持组合窗、转角窗、阳光房相关构件。
- 增加复杂场景测试用例。

验收标准：

- 新增窗型主要通过模板、系列配置和计算器扩展完成。
- 不影响已有平开、推拉窗型的 BOM 和报价结果。

当前进度：目标 9 已完成 —— BOM 计算器策略化（`BomCalculator` 接口 + 注册表：观景窗 → 推拉 → 上悬 → 平开/固定兜底，`computeBomFromDesignModel` 委派计算器，既有算料结果零回归）；新增**观景窗**（`tpl-view-large` 模板 + `ViewBomCalculator`，110 系列 `viewEnhance` 角色输出四角加强角码）；新增**组合窗**（`tpl-combo-two-fixed` 模板，多外框独立算料并汇总；校验对并排多框降为 info 提示、重叠多框保持警告；格子封闭分析按外框分别执行；画布适配器支持多外框重建与面板自动归属所在窗）；core 测试 68 项全绿。

## 八、近期优先级建议

建议优先做以下事项：

1. 统一设计数据源，让画布 `shapes` 能转换成可算料的 `DesignModel`。
2. 修复工具语义，把“矩形”改造成“外框/固定玻璃”等业务构件。
3. 实现基础 `computeBomFromDesignModel()`，先覆盖固定窗、平开窗、中梃、玻璃、五金。
4. 建立 75 平开和 120 推拉两个系列样本配置，用来验证不同系列算料差异。
5. 增加实时用料预览，让设计师绘制时直接看到材料影响。
6. 增加工艺校验，避免错误设计进入报价和下料。

## 九、关键判断

后续系统能否扩展，关键不在于继续增加多少绘图按钮，而在于是否打通以下链路：

```text
2D 图形数据
  -> 门窗构件数据
  -> 系列和窗型规则
  -> BOM 材料清单
  -> CuttingList 生产下料单
  -> Quote 报价单
```

一旦这条链路稳定，新增 120、110、75 系列，或新增平开、推拉、悬窗、观景窗、异形窗，都会变成配置和局部算法扩展，而不是对整个设计器反复重写。

## 十、第三方 Web 门窗设计工具可借鉴点

参考 `E:\WindowDoor-CAD-Toolkit-main\WindowDoor-CAD-Toolkit-main` 这类同为 Web 形态的门窗设计工具，其公开文档和项目结构里有几处很值得吸收：

### 1. 设计区、属性区、材料统计区分离

它把 `WindowCanvas`、`SettingPanel`、`MaterialStatsTable`、`DesignToolbar` 分成独立组件，说明门窗设计不该把“画图”“改参”“看料”揉成一团。

对我们的启发：

- 设计区只负责构件编辑和可视化。
- 属性区只负责系列、尺寸、五金、玻璃、颜色等参数修改。
- 材料区单独展示型材、玻璃、五金和成本变化。

### 2. 材料统计是独立工作流

它在 README 中明确强调“材料统计、成本估算、数据导出”。这和我们当前的目标一致：设计不是终点，算料和报价才是闭环。

对我们的启发：

- BOM 面板要常驻或半常驻，而不是藏在导出阶段。
- 设计修改后，材料统计必须实时刷新。
- 材料统计和报价要能独立查看，方便销售和生产两类人使用。

### 3. 模板库和保存加载很重要

其 PRD 提到模板库、自定义模板保存、设计方案保存与加载。这说明门窗软件需要强依赖复用，而不是每次都从零画。

对我们的启发：

- 尽快建立窗型模板库。
- 为高频方案提供一键复用。
- 保存的不只是图形，还要保存系列、窗型、颜色、五金和材料配置。

### 4. 3D 预览与纹理增强有助于方案沟通

该项目使用 Three.js，并带有木纹、玻璃等纹理资源，说明它非常重视方案展示和客户沟通。

对我们的启发：

- 3D 预览可以作为成交展示层，而不只是装饰。
- 3D 纹理和颜色选择要与 2D 设计参数一致。
- 可视化和算料必须来自同一设计模型，避免前后不一致。

### 5. 可本地化保存和离线能力

其实现中包含 IndexedDB、本地缓存、mock 数据和保存加载流程，说明在 Web 场景里，门窗设计需要考虑弱网或离线编辑。

对我们的启发：

- 本地自动保存非常必要。
- 方案草稿可以先落本地，再同步服务端。
- 设计器应支持断网情况下的有限工作能力。

### 6. 下料优化单独处理

它存在 `CuttingOptimizer` 之类工具文件，说明“算料”和“排料优化”在门窗场景里应当分开设计。

对我们的启发：

- BOM 负责汇总物料。
- CuttingList 负责逐根下料和排料优化。
- 不能把报价清单直接当生产清单。

### 7. 可以吸收，但不要照搬的点

- 可以吸收：分区式工作台、模板化设计、材料统计独立面板、保存加载、3D 预览、下料优化、本地缓存。
- 不建议照搬：把通用图形当成门窗业务构件、把 UI 功能堆成较重的配置面板、把模板和规则分散在多个视图里。

### 8. 可直接加入我们规划的补充项

建议在后续迭代中新增以下事项：

- 模板库面板：常用窗型一键插入。
- 材料统计面板：实时显示型材、玻璃、五金、辅料和成本。
- 本地自动保存：支持草稿恢复。
- 下料优化器：输出排料方案和余料。
- 3D 展示优化：展示纹理、玻璃、开启方向和颜色。
- 离线草稿能力：允许在网络不稳定时继续编辑。
